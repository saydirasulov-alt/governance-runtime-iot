E1.  CLOSED-LOOP SAFETY UNDER DISTRIBUTION SHIFT
==============================================================================
  Same model, same trace, same plant. Only the governance changes.

  ungoverned                 exposure  1185.3 C-min   peak  3.75 C   avail 100.0%   rb  0   -
  shipped, no rollback       exposure   954.8 C-min   peak  3.75 C   avail 100.0%   rb  0   -
  shipped + rollback         exposure   953.2 C-min   peak  3.81 C   avail 100.0%   rb  9   -
  corrected + rollback       exposure   727.7 C-min   peak  3.81 C   avail 100.0%   rb  5   -
  oracle + rollback          exposure     1.2 C-min   peak  0.16 C   avail 100.0%   rb  1   -

  Read the third and fourth columns together.

  Admission control alone:  1185 -> 955 degC-min.
  Adding ROLLBACK:         955 -> 953 degC-min.  That is 0.2%.
  Peak excursion:          3.75 -> 3.81 degC.  Rollback did not reduce the peak at all.

  Rollback, against a plant with thermal inertia, recovers almost nothing. It
  cannot: by the time the room has left the safe band and the runtime has
  restored a safe setpoint, the heat is already in the room, and getting it back
  out takes the tens of minutes that E2 measures. The exposure has been paid
  before the mechanism can act.

  What DOES work is not getting there. The oracle policy -- same runtime, same
  rollback, same plant, one extra predicate that happens to be right -- lands at
  1.2 degC-min. The runtime mechanisms are not the
  limiting factor. The policy's estimate of context is.

  And the deployable proxy for that context sits between the two: the corrected
  CO2 predicate leaves 728 degC-min, because under
  distribution shift CO2 stops tracking occupancy. That gap, 728 vs 1.2, is a
  measurement of how much residual PHYSICAL risk is attributable to the context
  estimator rather than to the governance runtime. That number is the paper.

E3.  IRREVERSIBILITY: WHERE ROLLBACK IS NOT AVAILABLE AT ALL
==============================================================================
  Some actuations cannot be undone by issuing another command: a compressor
  lockout, a fired suppression system, a purged tank. We model an actuator that
  LATCHES above 28 degC and ignores every command afterwards.

  shipped, latching actuator exposure  4951.7 C-min   peak  3.63 C   avail  10.8%   rb  1   FAILED_SAFE@1050m (irreversible actuation)

  Under the shipped policy the runtime loses authority and enters FAILED_SAFE.
  It does not claim to have recovered, because it has not: the room is latched
  hot and only a human can clear it. A rollback mechanism that reported success
  here would be lying. Under the corrected policy the intent is never admitted,
  so the irreversible actuator is never reached. Prevention is the only thing
  that works against irreversibility, and that is an argument for policy
  correctness, not for better rollback.

E6.  REJECTION SEMANTICS BEAT REJECTION ACCURACY
==============================================================================
  What should the runtime DO when it says no? A gate that only vetoes is not a
  controller: the actuator keeps tracking whatever setpoint it already held, and
  if the context has changed, that setpoint is now wrong too.

  Three fallbacks, applied to the SAME policy, on the SAME trace:
    hold        keep the current setpoint (a pure filter)
    checkpoint  revert to the last setpoint that provably held the room in band
    safe_state  command 21 degC, which lies inside BOTH bands and is therefore
                safe without knowing which one applies

  oracle / hold              exposure   924.8 C-min   peak  3.95 C   avail 100.0%   rb  6   -
  oracle / checkpoint        exposure   918.7 C-min   peak  3.95 C   avail 100.0%   rb  5   -
  oracle / safe_state        exposure     1.2 C-min   peak  0.16 C   avail 100.0%   rb  1   -

  corrected / hold           exposure   734.0 C-min   peak  3.75 C   avail 100.0%   rb  6   -
  corrected / checkpoint     exposure   727.9 C-min   peak  3.75 C   avail 100.0%   rb  5   -
  corrected / safe_state     exposure   727.7 C-min   peak  3.81 C   avail 100.0%   rb  5   -

  A PERFECT gate with a naive fallback leaves 925 degC-min.
  An IMPERFECT gate with a context-safe fallback leaves 728 degC-min.
  The perfect gate WITH the context-safe fallback leaves 1.2 degC-min.

  So the fallback dominates. An oracle-accurate gate that reverts to a
  context-blind state is beaten by a far less accurate gate that reverts to a
  context-independent safe one. This is invisible in a software-only testbed,
  where restoring a variable is instantaneous and all three fallbacks look the
  same. It is only visible because the actuator is stateful and the room is slow.

E7.  THE ROLLBACK BUDGET DOES NOT BIND HERE, AND SAYING SO MATTERS
==============================================================================
  A rollback budget is meant to stop the runtime from undoing the same mistake
  forever: if it is rolling back every few minutes, the model is systematically
  wrong, and the honest response is to hand the zone to the fallback thermostat
  and call a human. We implemented it, and then we checked whether it ever fires.

  shipped, budget=unlimited  exposure   953.2 C-min   peak  3.81 C   avail 100.0%   rb  9   -
  shipped, budget=10         exposure   953.2 C-min   peak  3.81 C   avail 100.0%   rb  9   -
  shipped, budget=5          exposure   953.2 C-min   peak  3.81 C   avail 100.0%   rb  9   -
  shipped, budget=3          exposure   953.2 C-min   peak  3.81 C   avail 100.0%   rb  9   -

  It does not. Every setting gives an identical result, because the shipped
  policy triggers only 9 rollbacks in 163 hours -- never three within any one
  hour -- so no budget in this range is ever reached.

  This is worth reporting rather than quietly dropping, for two reasons. First,
  a mis-tuned variant of this experiment CAN exhaust the budget and enter
  FAILED_SAFE within a few hours, which looked like a meaningful safety result. It
  was not: the monitor had no deadband and was firing rollbacks on 0.01 degC of
  sensor noise. The budget was measuring a bug in our monitor, not a property of
  governance. Second, it means the ONLY condition under which this runtime
  legitimately reaches FAILED_SAFE in our workload is irreversible actuation (E3).
  A mechanism that never fires is not a contribution, and we do not present it as
  one.

==============================================================================
WHAT THE SWEEP SAYS
==============================================================================
  It is a THRESHOLD, not a gradient. That is the useful part.

    plants slewing at 6.9 degC/min or faster (tau <= 5 min):
        rollback removes at least 95% of the unsafe exposure
    plants slewing at 1.4 degC/min or slower (tau >= 27 min):
        rollback removes at most 4.8%

  The system either wins the race against the next bad command on every cycle
  or it loses on every cycle; the transition between the two is narrow. Rollback
  undoes ONE command, and a systematically wrong model simply issues it again on
  the next cycle, so the runtime has to be able to restore the plant well inside
  the 60 s between decisions or it never catches up at all.

  A NOTE ON THE RECOVERY-TIME COLUMN. Do not use it as the predictor. It is a
  median over excursions that DID recover, so on slow plants -- where many
  excursions never recover before the trace ends -- it is biased low and can even
  fall as the plant gets slower. The slew rate is the honest independent
  variable, because it is a property of the plant rather than of the outcome.

  UPPER BOUND -- the plant is too slow. The building in this paper
  (tau = 3.0 h, 0.21 degC/min) sits far above the threshold:
  rollback removes 0.1%. Sampling faster does not help, because the
  bottleneck is the room, not the sensor.

  LOWER BOUND -- the monitor is too slow. On the fastest plants a 30 s monitor is
  worth a fraction of a 1 s one: the plant leaves the safe band between samples,
  so the runtime only ever sees the aftermath. Here the bottleneck IS the sensor,
  and unlike the room it is fixable.

  BEST CASE in this sweep: 99.0% (tau = 1 min, monitor 1 s).

  So the honest claim is not 'rollback does not work'. It is:

      Runtime rollback delivers safety when the plant can be restored faster
      than the next bad command arrives, and sampled faster than it can leave
      the safe set. Outside that band it degrades into a bookkeeping mechanism:
      a correct audit trail and a defined terminal state, but not safety.
      Safety there has to come from admission control, and admission control is
      only as good as the policy's estimate of context.

  Every quantity in that criterion is measurable on a real system before any
  code is written: the actuator's recovery time, the control period, and the
  monitor's sampling rate.

==============================================================================
2b. DOES IT DEPEND ON THE SENSOR-NOISE *LEVEL*?
==============================================================================
  Changing the seed re-rolls the same noise. Changing sigma changes how MUCH of it
  there is, and that is the question a deployment actually asks: our sensor is not
  your sensor. A cheap thermistor is an order of magnitude noisier than the
  0.05 degC we assume, and a conclusion that turns on that assumption is not a
  conclusion.

  The monitor's deadband is DERIVED from sigma (five sigma), not fixed. A fixed
  0.25 degC deadband at sigma = 0.5 is half a standard deviation -- no deadband at
  all. The monitor would fire on noise and the rollback count would measure
  chatter, so the experiment meant to VALIDATE the monitor would have been
  measuring a bug in it. We made exactly that mistake once; E7's budget was
  measuring it.

  sigma 0.05 C  deadband 0.25  norb   954.8  rb   953.2 (  0.2%)  corr   727.7  orac    1.2   C1 y C2 y C3 y
  sigma 0.25 C  deadband 1.25  norb   954.8  rb   951.3 (  0.4%)  corr   728.0  orac    1.8   C1 y C2 y C3 y
  sigma 0.50 C  deadband 2.50  norb   954.8  rb   954.4 (  0.0%)  corr   728.1  orac    1.8   C1 y C2 y C3 y

  The no-rollback exposures are IDENTICAL across the three noise levels, and
  they MUST be: the oracle scores the TRUE plant temperature, and no amount of
  sensor noise changes the truth. What noise can change is the MONITOR's
  decisions -- and with the deadband tracking sigma, it does not change them
  enough to move a single claim.
  This is also the check that would have caught our worst bug. An earlier
  version added noise by patching the ORACLE, which let sensor noise leak into
  the ground truth and produced the conclusion that 'sensor noise makes rollback
  27% more effective'. A result that absurd is a bug report, not a finding. The
  fix was to give the monitor and the scorer separate eyes, and this experiment
  is what proves they stayed separate.

3.  DOES IT DEPEND ON THE 30-MINUTE GRACE WINDOW?
==============================================================================
  We log a grace-free exposure on every run and have never once looked at it.
  A number you compute and never read is not a safeguard, it is decoration.

  NO grace window:             norb  1339.4  rb  1337.6 (  0.1%)  corr  1109.6  orac   130.1
                               C1 HOLDS | C2 HOLDS | C3 not applicable (see floor)

  THE FLOOR. Replace the AI service with one that CANNOT be wrong:
    perfect model, 22/17 setback   grace     0.0   strict   337.0
    constant 22 C, no setback      grace     0.0   strict     0.0
    ORACLE GATE, real model        grace     1.2   strict   130.1

  A perfect model scores exactly 0.0 under the grace window, which is what
  makes the window the right instrument: it counts only what a controller
  could have avoided. Under strict scoring the same perfect model pays 337 --
  the ramp cost of the 22/17 SETBACK STRATEGY, which a no-setback controller
  pays 0 of. The oracle gate's 130.1 sits BELOW even that, so it is not a
  governance failure. It is the control strategy's bill, and we should not
  have been charging it to the runtime.

  The grace window forgives the ramp the plant physically cannot skip. Without
  it every arm carries the same large unavoidable offset, so the ABSOLUTE numbers
  rise. What matters is whether the ORDERING and the CONCLUSIONS survive.
